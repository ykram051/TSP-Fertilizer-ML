\chapter{Deployment and Implementation}\label{ch:deploy}

\section{Architecture and safety boundary}
The implementation is a staged, advisory-only architecture (Figure~\ref{fig:deployment-architecture}). Sensors and laboratory results are handled by the PLC/DCS layer; Kepware is the intended industrial gateway, communicating southbound with approved plant protocols and exposing configured tags northbound through OPC UA \citep{opcua}. A containerised Python service subscribes to these tags, builds features, predicts, and writes to a runtime volume holding the SQLite audit database and a health file. A native desktop dashboard on the host reads that volume read-only. The optional advisory OPC namespace is disabled by default (\var{advisory\_write\_enabled: false}).

The model has no path to PLC/DCS setpoints, controller modes, interlocks, permissives, valve or pump commands, or safety logic, and a service, network, database or dashboard failure leaves control unaffected. Plant integration follows the staged roadmap of Table~\ref{tab:stages}. The laboratory configuration runs on an isolated Docker network with OPC security disabled (\var{security\_mode: None}); the plant configuration uses the security profile of Table~\ref{tab:security}.


\section{Three-stage deployment roadmap}
Deployment is organised in three stages whose exit criteria are explicit (Table~\ref{tab:stages}). Stage~1, the subject of this report, validates the software chain on replayed history; Stages~2 and~3 extend it to a laboratory gateway, then to read-only shadow operation and an advisory display. The OPC UA link itself is specified in Table~\ref{tab:security}: the inference service is the \emph{client} and Kepware (or the simulator) the \emph{server}, and the client subscribes to the sequence tag rather than polling every sensor.

\section{Containers, configuration and storage}
Docker Compose defines two services on an isolated bridge network: an OPC UA CSV-replay simulator and the inference service, both on Python 3.11 slim images. The inference image installs \texttt{libgomp1} for LightGBM, defines a health check and mounts configuration, model artifacts, schema and runtime output. Settings can be overridden through environment variables, and Node IDs live in \texttt{opc\_tags.yaml}, not in code. Table~\ref{tab:config} gives the main parameters.

SQLite is the authoritative Stage~1 audit store, with JSONL and latest-JSON mirrors for inspection. It is opened in WAL mode with foreign keys and a 10-second busy timeout, so a read-only dashboard can query history while the service writes. Three tables (Table~\ref{tab:schema}) make every output traceable to a run and a source timestamp; \texttt{UNIQUE(run\_id, sequence)} prevents duplicate predictions. This suits a one-writer laboratory demonstration and is not a replacement for a plant historian, retention policy or backup design.

\section{Streaming pipeline and quality controls}\label{sec:pipeline}
Stage 1 replays the confidential CSV without plant access: the simulator publishes each row as OPC UA tags, sets the source timestamp and then writes a sequence number as a commit marker; it can refresh the simulated laboratory target every 60 rows. The service avoids mixed snapshots with a \emph{sequence-read-sequence} protocol: it reads the sequence, then all input tags, then the sequence again, and accepts the row only if both sequence values agree.

Accepted snapshots pass the quality shield (Table~\ref{tab:quality}). Isolated missing cells are tagged \texttt{IMPUTED} and handled by the saved training-fitted imputer and missingness indicators; nothing is ever fitted during live inference. The rolling buffer additionally refuses non-monotonic timestamps and clears its history when a source gap exceeds cadence plus tolerance (65 s), because rolling features must not silently bridge a gap.

\begin{table}[!htbp]\centering\small\zebra
\caption{Data-quality rules applied to every snapshot.}\label{tab:quality}
\begin{tabularx}{\textwidth}{L{0.30\textwidth}YL{0.18\textwidth}}\toprule
\thead\hd{Rule} & \hd{Condition} & \hd{Outcome}\\\midrule
Missing inputs & $\le25\%$ of required tags missing & accepted, \texttt{IMPUTED}\\
Missing inputs & $>25\%$ missing & \texttt{DATA\_ERROR}\\
OPC quality & any required tag bad or uncertain & \texttt{DATA\_ERROR}\\
Engineering limits & value outside configured minimum or maximum & \texttt{DATA\_ERROR}\\
Chronology & non-monotonic timestamp or gap $>65$ s & rejected or buffer reset\\
Laboratory target & missing, future-dated or older than 120 min (anchored mode) & \texttt{DATA\_ERROR}\\\bottomrule
\end{tabularx}
\end{table}

\section{Warm-up and operating modes}
The maximum feature lookback is 30 minutes, so a cold start needs the current row plus 30 previous rows: 31 accepted rows before the first valid prediction. Until then the service reports \texttt{WARMING\_UP} and does not fabricate history; historian backfill would be the production improvement. In \texttt{target\_free} mode the service estimates the current value from process signals. In \texttt{target\_anchored} mode it requires the current laboratory value with its timestamp and produces 1-, 5-, 10- or 15-minute delta forecasts, which protects it from treating an outdated laboratory result as a live analyser.

\subsection{Processing sequence}
Each minute the service executes the following steps; the complete flow is summarised in Figure~\ref{fig:sequence}.
\begin{enumerate}
\item Receive the sequence notification and read sequence, mapped inputs and sequence again.
\item Apply the quality shield (Table~\ref{tab:quality}); isolated gaps become \texttt{IMPUTED}.
\item Append the accepted row to the chronological buffer; publish \texttt{WARMING\_UP} until 31 rows exist.
\item Build the feature columns expected by the saved artifact and apply the training-fitted preprocessing, never refitting live.
\item Run \texttt{target\_free} estimation or the configured \texttt{target\_anchored} forecast.
\item Commit the record to SQLite in one transaction, then mirror it to JSONL and latest-JSON files.
\end{enumerate}
